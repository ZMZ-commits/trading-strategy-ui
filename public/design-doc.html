One workspace volume is mounted into all three backends

Datasets are properly separated — dataset_dev, dataset_stg, dataset_prod are distinct volumes. Strategies are not. A single workspace volume is shared by every backend and the sandbox, which is why a strategy published to dev appears in production immediately. That is convenient today and unacceptable the moment more than one person can publish.

The Terraform in the repo targets AWS, not the server you are on

infrastructure/terraform/ provisions ECR, EC2, EBS, S3 and CloudFront. The live deployment is Hetzner plus docker compose plus GHCR. So the infrastructure code and the running system have drifted apart entirely — worth knowing before treating that directory as a description of reality.

What does not exist yet: any authentication, any database, orgs and projects, bar storage, Kafka, the bot, and all observability.

What it does say is that sequencing matters more than speed: fourteen things do not exist, and the order they arrive in decides whether the platform is usable at each step or only at the end.

Tenancy

Org holds people. Project holds work.

An org is a group of users. A project is a workspace inside it — its own datasets, strategies, watchlists and labels. Opening Lab means picking a project first, and what you see afterwards is only what that project owns.

Membership is two-layer on purpose. Being in the org does not grant a project; a project grant does. That is what lets one person work across several projects while another sees exactly one.

orgs(id, name)
projects(id, org_id, name)
users(id, email, name, password_hash, provider)

org_members(user_id, org_id, role)          -- owner | admin | member
project_members(user_id, project_id, role)  -- admin | editor | viewer

-- everything else carries project_id
datasets(id, project_id, ...)   strategies(id, project_id, ...)
watchlists(id, project_id, ...) labels(id, project_id, ...)

Collection dedupes across projects; access does not

Three projects watching AAPL produce one subscription and one copy of every bar — the symbol registry reference-counts across the whole platform. But each project only sees the bars its own permissions allow. Shared cost, separate access.

node-1 up close — what calls in, what it calls out

Same rule as node-2: every arrow starts at a service and ends at a service. Solid runs today, dashed does not. Observability is left out deliberately — it scrapes everything and would add fourteen lines that say nothing about how the product works.

The second column is the designed path: each view presents a session to auth, auth resolves org, project and grants, and only then does it authorise the service being asked for. Every one of those arrows is dashed because none of it is built. The single solid arrow across the top is the real one — the browser reaching the services directly, with the gate standing beside the traffic rather than in it. The tag in the corner of each service says which view actually uses it.

Each view owns a colour, and it keeps that colour the whole way through — into the gate, and back out of it to the services that view is allowed to reach. TPIAM is the clearest one to follow: one line in, one line out, ending at the org and project manager and nowhere else. Trading and Lab both reach the history service, which is why it is the only box with two lines arriving in two colours. The same three colours are used in the cascade at the top of this section, so a path can be followed between the two drawings.

The market data on this machine does not come from Alpaca

The blueprint shows Alpaca as the feed, and for live ticks that is right — the pipeline on node-3 subscribes to it. But every historical bar node-1 serves comes from Yahoo Finance, through the yfinance package: services/yfinance_service.py for single pulls and services/history_job_service.py for long ones, which it assembles out of roughly seven-day requests because that is Yahoo’s ceiling for minute data. services/dataset_service.py does the same and caches the result on disk so the Lab is not re-pulling constantly.

So there are two market data providers in production right now, not one — Alpaca for the live stream, Yahoo for everything historical — and they are not reconciled against each other. That is worth deciding on deliberately rather than discovering when a backtest and a live chart disagree about the same minute.

Answers to what calls what

  • Redis — one caller on node-1: the live tick socket. It subscribes to ticks:{SYMBOL} and reads price:{SYMBOL} on connect. Nothing else on the machine touches it.
  • TimescaleDB — no caller at all. Three services would eventually read it (history, sandbox worker, org manager) but none can: there is no database driver in the repository.
  • dbt — no caller, and there never will be one. It is a scheduled job, not something a service calls. See node-2 up close.
  • node-3, the stream — nothing on node-1 calls it. The planned link is the symbol registry telling the scraper what to subscribe to; today the two machines are joined only indirectly, through Redis.
  • Service to service inside node-1 — exactly one hop exists: datasets calls the sandbox worker over HTTP on port 9000 to execute a strategy (dataset_service.py → sandbox_client.run_strategy). Strategy runs does not use the sandbox — it imports the engine in-process through engine_adapter.py, which means backtests run unsandboxed inside the API process.
  • Cloudflare to node-1 — the browser calls each route directly. There is no gateway and no auth: main.py adds CORS middleware and mounts seven routers, and CORS is the only thing standing in front of any of them. CORS is a browser convention, not a lock — it is enforced by the caller, so anything that is not a browser ignores it completely.
  • Which view uses which service — Trading uses the live tick socket and the history service. Lab uses the history service, datasets and strategy runs, and reaches the sandbox worker only indirectly through datasets. TPIAM has exactly one callee, the org and project manager, and neither end of that pair exists yet.

The symbol registry: nothing uses it, and that is the problem

No service calls it, because it does not exist. What makes it worth building is that both ends it would join are already there, and they are not connected to each other.

  • The watchlist is real, and it never leaves the browser. ui/src/data/watchlist.ts and TopPanel/AddToWatchlist.tsx hold it as persisted client state. Nothing posts it anywhere — there is no fetch to any endpoint in that path at all.
  • The scraper subscribes to a hardcoded list. data-pipeline/src/ingestion/alpaca_ws.py has DEFAULT_SYMBOLS = ["AAPL", "TSLA", "NVDA", "MSFT", "AMZN", "GOOGL", "META", "SPY"] and subscribes to those eight, always.

So adding a symbol to your watchlist today changes nothing about what is being collected. You can watch a ticker that is never scraped, and all eight are scraped whether or not a single person is watching them. The registry is the piece that would make the watchlist mean something — which is why its arrow to the scraper is the one dashed line that changes the behaviour of two machines at once.

Should the registry be a table instead of a service? Mostly yes.

It is worth splitting the question, because “registry” is being asked to mean two things: a list (which symbols, who wants them, since when) and a decision (what the scraper subscribes to right now).

The list belongs in the database, and only there. It has to survive restarts, it has to be queried alongside the bars it explains, and the watermark question — do we already hold this range? — is a join against the same rows. Holding it in a service’s memory would mean the answer changes when a process restarts, which is the one thing it must never do. One table: symbol_tracking(symbol, tracked_since, watchers).

The service in front of it is the part I would drop. A registry service exists only to be asked “what should I watch?”, and the scraper can ask the table that question itself. Deleting the box removes the only call node-1 would ever make into node-3, which is the most awkward arrow in the whole design — it makes the edge machine responsible for reaching into the pipeline and pushing it around. Let the scraper reconcile against a table on a timer instead, and the dependency reverses into something ordinary: node-3 reads its own configuration, and nothing pushes anything.

Writes stay where they already are. The Lab and Trading views add a watch, the API bumps watchers, and that is the whole write path — no new service, no RPC, no ordering problem when two people watch the same ticker at once.

And it does not have to wait for TimescaleDB

The obvious objection is that none of this can start until the database exists. It can. The backend and the scraper both already hold a Redis connection — that is the one piece of node-2 that works — so a Redis set of watched symbols, with the scraper reconciling its subscriptions against it every few seconds, closes the gap between the watchlist and the eight hardcoded tickers now, with no schema and no driver.

The cost is honest: Redis is not durable enough to be the permanent home of who-watches-what, and a few seconds pass before a newly watched symbol starts collecting. Neither matters at this size. Move the set into symbol_tracking when the database lands and the scraper changes one query — but the feature does not need to be blocked behind it.

The sandbox worker: Trading and Lab both, TPIAM never

I had this wrong in the first version of the diagram — I had it reached only through datasets, which made it look like a Lab-only concern. It is not.

  • Trading reaches it through custom indicators. StockChart calls useCustomIndicators, which hits /custom and /stocks/{ticker}/custom/{slug}, and routes/custom.py forwards straight to sandbox_client.
  • Lab reaches it twice over: the same chart component — LabPage renders the very same StockChart — plus dataset backtests, where dataset_service.py calls sandbox_client.run_strategy.
  • TPIAM does not touch it.

Worth sitting with: the live Trading chart executes user-authored code on every custom indicator you add. That path is sandboxed, which is the good news. The path that is not sandboxed is the one that sounds safest — strategy runs, which imports the engine in-process.

node-2 up close — who actually touches the data

Every arrow here leaves a service and lands on a service. Solid means it runs today; dashed means the caller, the callee, or both are still on paper.

node-2 readiness: one of the three boxes is real

I checked all five repositories rather than reading this off the plan.

  • Redis — built and running, with exactly two users. The scraper writes it (data-pipeline/src/storage/redis_store.py — PUBLISH ticks:{SYMBOL} for the stream, SET price:{SYMBOL} with a one-day expiry so a client connecting mid-session is not staring at a blank chart). The live tick socket reads it (backend/src/routes/live.py — subscribes to that channel, sends the cached price on connect, then forwards every tick to the browser over /ws/live/{ticker}).
    Alpaca → scraper → Redis → socket → chart is the one path in the whole blueprint that runs end to end today. Redis carries live ticks only — not sessions, because there is no auth yet to have sessions.
  • TimescaleDB — not started, and further off than it looks. No repository contains a database driver at all: the backend’s requirements list fastapi, uvicorn, yfinance, pydantic, httpx and redis, and nothing else. There is no asyncpg, no psycopg, no sqlalchemy, no DATABASE_URL. Bars are fetched per request and thrown away; strategies are JSON files under STORE_ROOT.
  • dbt — not started. Zero references across all five repos: no dbt_project.yml, no models/, no mention in any dependency file.

The order is forced: dbt transforms tables that a database has to hold first, so it cannot be started until TimescaleDB exists and the pipeline is writing into it. It is the last thing on node-2, not a parallel track.

What dbt is, in one paragraph, because the box is misleading

dbt is not a service. It has no port, nothing connects to it, and it is not running most of the time. It is a batch job: a scheduler starts it, it issues a long series of CREATE TABLE AS SELECT statements against TimescaleDB, and it exits. Its input is the raw tables the pipeline wrote; its output is mart tables sitting in the same database beside them.

So the answers are: nothing uses dbt — only the scheduler starts it. dbt calls exactly one thing, TimescaleDB, and both its read and its write go there. And nothing sits on top of dbt — when the history service or a Grafana panel reads a mart, it is running an ordinary query against Timescale and has no idea dbt produced the table. That is why removing dbt would not break any connection; it would just leave the mart tables frozen at their last build.

Which jobs are worth handing it — and which two it should be kept away from — is set out in Where dbt earns its place.

One correction to the sizing intuition

The natural reading is that node-3 does the heavy computing and node-1 is the modest one in the middle. Today it is the other way round. node-1 runs the API and the sandbox worker, and the capacity numbers in this document say the sandbox starves the API before anything else on any machine gives way. node-3 is mostly waiting on a socket — a scraper holding one websocket open is close to idle.

That matters for this question because it rules out the option that looks appealing: putting the telemetry stores on node-3 to use its spare capacity is the worst of the three placements. A node-3 failure would take out the pipeline and the alerting that would have told you about it — the one failure mode where silence and health look identical. Spare capacity is not a good enough reason to put the smoke alarm in the room most likely to catch fire.

Should observability get its own node? Yes — but it is the second one you buy

It is the right end state. A machine cannot credibly monitor itself, and two time-series stores sharing a disk with the database is a compromise, not a design. Roughly nine dollars a month buys the whole problem away.

But the sandbox should move first. The capacity work already says node-1 is where the ceiling is, and moving the sandbox off it is what buys headroom on the machine that is actually short. Observability on node-2 is uncomfortable; the API and the sandbox competing on node-1 is the thing that will bite first.

So the order is: node-4 takes the sandbox, node-5 takes observability. Until then the dead-man’s switch is what makes node-2 an acceptable home rather than a bad one.

The trigger to stop waiting

Do not do it on a schedule — do it on a number. Move observability off node-2 when any one of these is true:

  • Prometheus resident memory passes 1 GB, which at this shape means somewhere north of a hundred tracked symbols.
  • The node-2 volume passes 70% with retention already trimmed once.
  • You see Timescale query latency rise at market open specifically — that is the page-cache contention arriving, and it is the symptom the earlier argument predicted.

All three are things the stack you are about to install will tell you itself, which is the point: the monitoring decides when the monitoring needs to move.

The rule that decides where anything new goes

Two lines, and they settle every question of this kind without re-arguing it:

  • If it stores things, it goes on node-2. TimescaleDB, Redis, Prometheus, Loki, Tempo, and dbt which rewrites tables in place. node-2 is the machine with the volume, the backup, and the disk budget — and keeping every store together means there is exactly one machine whose disk you have to watch.
  • If it is a front end, it goes on node-1. The API, and Grafana. node-1 is the only machine the browser can reach, so anything a person looks at belongs there and nothing else has to be exposed.

Everything left over is a worker, and workers go wherever the load says — the sandbox on node-1 for now because the API calls it synchronously, the pipeline on node-3 because it holds the socket. Alertmanager is the one deliberate exception: it stores nothing and nobody browses it, but it belongs beside Prometheus so an alert does not need a working network hop to be routed.

The rule has a cost, already noted above: putting the telemetry stores on node-2 means node-2 cannot report its own death. That is what the external dead-man’s switch is for, and it is the reason that switch is the first alert in the table rather than the last.

What it costs to run

Roughly 1.2 to 1.5 GB of RAM across all three machines and about 2 GB of disk for fifteen days of metrics at eight symbols, plus whatever you give Loki. On CX32s that is comfortable. Licence cost is zero and there is no per-user or per-sample billing, which is the whole reason this stack rather than a hosted one — Grafana Cloud and Managed Prometheus both bill on dimensions that grow exactly when you add symbols.

Start with four containers: Prometheus, Alertmanager, Grafana, node_exporter. That is a working stack in an afternoon. Add postgres_exporter and redis_exporter when TimescaleDB lands, Loki when you first wish you had it, and kafka_exporter with Kafka. Tempo is worth pulling forward — it is one container plus three lines in main.py, and it answers the question metrics never can: which hop was slow.

Metric, log, or record? Decide this first

Almost every mistake in observability is putting a signal in the wrong one of these. They are not interchangeable and they fail in different directions.

Metric · PrometheusLog · Loki Record · TimescaleDB
ShapeA number over timeA line of text A row with columns
AnswersHow many, how fast, how often What happened, in wordsWhat exactly happened, and why
Kept15 days, downsampledWeeks Forever
Lossy?Yes, by design. Sampled at a scrape interval — events between scrapes are simply not there Only if you drop itNo
Joinable to bars?NoNo Yes — same database, same time index
Alert on it?Yes, this is its job Rarely, and it is expensiveVia a scheduled check

The rule: if you would ever need to prove it happened, or join it against price data, it is a record — not a log and not a metric. Metrics tell you the shape of a day. Records let you reconstruct one.

This is why the instinct to send bot decisions to both Prometheus and TimescaleDB is the correct one. They are not duplicates. The metric answers “has the bot gone quiet?” at 3am, in one query, across every strategy. The record answers “why did it buy AAPL at 10:32 on the 14th?” three months later, with the indicator values it saw. Neither store can answer the other’s question, and losing the second one is unrecoverable.

The bot’s decisions — the one that needs both stores

Everything else on this page is operations. This is the part where getting it wrong costs money rather than sleep, so it is worth doing twice over.

As metrics, for alerting

SeriesTypeWhat it catches
bot_signals_total{strategy,symbol,side}counter Firing rate per strategy. A strategy that suddenly doubles its rate has usually broken, not improved.
bot_skipped_total{strategy,reason}counter The one people forget. Counting only what fired means a silent bot is indistinguishable from a correctly-patient one. Counting the reasons it declined is how you tell “no setup today” apart from “the indicator has been returning NaN since Tuesday”.
bot_decision_latency_secondshistogram Time from bar.closed to decision. If this drifts past a few seconds the bot is trading a bar the market has already moved past.
bot_last_decision_timestampgauge Powers the only alert that matters overnight: no decision of any kind during market hours.
bot_open_positions{strategy}gauge Divergence from the broker’s own count means state has drifted.

As records, for everything else

One row per decision, in TimescaleDB, including the ones where it decided not to act:

  • When — decision time and the bar time it acted on. These differ, and the difference is a bug when it grows.
  • What — strategy id and version, symbol, side, size, price.
  • Why — the rule that fired, and the indicator values it saw at that moment. Without these you can never answer whether a bad trade was bad logic or bad data, because recomputing them later gives you today’s data, not what it had.
  • Why not — for skips, the reason. This is the column that turns a quiet week into something you can read.
  • The trace ID — see below.

One column that ties all three stores together

Store the trace ID on every decision row. It costs one column, and it turns three separate systems into one investigation: you find a bad trade in a SQL query, paste its trace ID into Tempo to see exactly which calls the decision made and how long each took, and jump from there into the Loki lines that same request emitted.

Without it you have three tools that each know part of the story and no way to line them up by anything better than a timestamp.

Watching the UI, which no server-side metric can see

The UI is served by Cloudflare Pages, so none of your machines ever sees a page load. Two approaches, and you want both.

  • Synthetic — blackbox_exporter for reachability and TLS, already in the stack. For real page timing on a schedule, Grafana k6 (open source, exports to Prometheus) scripted against the app.
  • Real user monitoring — Grafana Faro, the open-source browser SDK. Web Vitals, JS errors, and — the reason to prefer it over a bare web-vitals package — it propagates trace context, so a click in the browser and the backend span in Tempo become one trace. It needs a receiver (Grafana Alloy) on node-2.

But the numbers that matter here are custom. Web Vitals measure page load, and page load is not where a charting app feels slow. Time-to-first-bar, frame time during pan and zoom, and websocket time-to-first-tick are performance.mark() calls shipped through the same beacon. Every chart regression in this project so far was found by a person noticing, not by anything measuring.

k6 has one job worth doing early: find where the sandbox threadpool falls over. Concurrent dataset backtests hit blocking urllib calls from a finite pool, and nobody has measured that ceiling. Better to find it on a Tuesday than during a demo.

Reading the pipeline

Kafka is drawn as a column because it is a bus, not a step. The scraper publishes ticks into it; the aggregator and analytics each consume independently. The aggregator then publishes a closed bar back into Kafka, and the bot host consumes that — which is why the trigger arrow points out of Kafka rather than out of the aggregator. Kafka carries the trigger, TimescaleDB carries the history.

The only line running the other way between machines is node-1 telling node-3 which symbols to watch. Nothing on node-1 reads from the pipeline directly; it reads bars from node-2 like everything else.

Why the telemetry stores sit on node-2

Prometheus and Loki are both time-series stores, and node-2 is the machine with the disk and the volume. Putting them there also takes load off node-1, which the capacity numbers say is the constrained one — the sandbox starves the API before anything else gives way, so every process moved off it buys headroom where headroom is scarce. Grafana stays on node-1: it is a reader, it stores almost nothing, and it belongs next to the thing you already log into.

The cost of this is real and worth naming. Two time-series stores share one page cache, and they compete hardest at the worst moment — market open, when Timescale is taking writes and Prometheus is scraping fastest. At eight symbols Prometheus is small enough that this stays theoretical: a few thousand series, a couple of hundred megabytes of RAM. It stops being theoretical somewhere around a few hundred symbols, and that is the point to give observability its own node rather than to tune retention around it.

The second cost is sharper: monitoring that lives on node-2 cannot tell you node-2 has died. That is covered below, and it is not optional.

Whichever machine watches the others cannot watch itself

With the stores on node-2, a node-2 failure takes out the database and the alerting that would have told you — the one failure mode where silence is indistinguishable from health. Grafana on node-1 would still be up and would simply show nothing, which is worse than an error because it looks calm.

The fix is a dead-man’s switch, and it costs nothing. Alertmanager is given one alert that always fires — a Watchdog rule matching everything — routed to an external service such as healthchecks.io on its free tier. That service expects a ping every few minutes and alerts you when the pings stop. It is the only alert that works by absence, and it is the only one that survives the machine it runs on going dark.

Without it, moving the stores to node-2 is a downgrade. With it, the blind spot is covered by something that does not share a rack, a disk, or a power supply with anything in this diagram.

Why the execution boxes are drawn open

The sandbox is amber, but not because it needs rewriting. Only the inner loop moves to Rust; the Ctx API that strategies are written against stays exactly as it is. Drawing the two apart is the difference between “rewrite the sandbox” and “compile the part underneath it” — and the bot host reuses those same kernels, which is what keeps a live decision and a backtest arithmetically identical.

Kafka is your call, and it is now in the design

I argued for Redis Streams on a single host and you have chosen Kafka, so the plane is drawn around it. The shape you described — one producer, many independent consumers each at their own offset — is genuinely what Kafka is for, and the bot makes a third consumer. Budget for it: a JVM broker wants roughly a gigabyte before it does any work, competing with TimescaleDB on the same box. If that box is small, Redpanda speaks the same protocol without the JVM.

The bot

Fire on closed bars, not on ticks

You asked what the right trigger is, and for the bot to be accurate about timing. This is the one decision in the whole design where getting it wrong is expensive, because it decides whether live trading and backtesting ever agree.

Every strategy you have is defined on closed bars. The opening range waits for 09:45 to complete; the SMA crossover compares finished candles; the chandelier stop reads a bar high. Triggering on ticks means evaluating a bar that is still changing, and a signal that appears mid-minute can vanish before the minute ends.

The grace period matters for the same reason. Prints arrive late and out of order. Sealing the bar the instant the clock rolls over means the aggregator may later have to correct a bar the bot has already traded on.

The real prize is backtest parity

A bot that wakes on bar.closed and queries TimescaleDB for its lookback window sees exactly what ctx.bars() sees in a backtest — same bars, same order, same completeness. Any other trigger means live and backtest diverge, and then neither number can be trusted. This is what makes an ORB result on 18 sessions mean something when the bot runs it live.

  1. Aggregator seals the minute

    Two seconds past the boundary, so late prints are in.

  2. Publish bar.closed

    One Kafka message per symbol per minute. Small, ordered, replayable.

  3. Host wakes the bots bound to that symbol

    Only strategies enabled in a project that watches it.

  4. Bot reads its lookback from TimescaleDB

    Kafka carries the trigger; the database carries the history. The bot never keeps state it would lose on restart.

  5. Decide, and record the decision either way

    “No trade” is a result worth storing — it is what you compare against the backtest.

A restart must not re-fire yesterday’s orders

Kafka replays. That is its value and its hazard: a consumer that restarts and re-reads the topic will see every bar.closed again. Every decision needs an idempotency key of (strategy, symbol, bar_ts) checked before acting, so a replay recomputes and finds the decision already recorded instead of placing a second order.

Where a minute comes from

One watermark per symbol

Once a symbol is tracked, minutes accumulate continuously, so coverage is a single range that only grows — forwards as collection runs, backwards when pre-tracking history is backfilled. A request splits at tracked_since: after it comes from your database, before it comes from a provider once and then becomes yours too, and earlier than both is reported as unavailable rather than quietly truncated.

Only 1-minute bars are stored. Hourly and daily are TimescaleDB continuous aggregates — computed, self-refreshing, never a second copy that can drift after a backfill.

symbol_tracking(symbol, tracked_since, watchers)   -- the whole ledger
bars(symbol, ts, o, h, l, c, v, UNIQUE(symbol, ts)) -- hypertable
bar_gaps(symbol, gap_start, gap_end)                -- usually empty

What each repository is responsible for

ui renders and never decides. backend owns every policy question — who may do what, which project a thing belongs to, where a bar comes from. engine owns strategy semantics and is the only place strategy code executes, backtest or live. data-pipeline owns everything between a market feed and a stored bar. platform owns the machines and how it all gets deployed.

The seam that matters most: the backend never executes strategy code and the engine never makes access decisions. Keeping that line clean is what lets the sandbox be locked down later without touching the API.

Three things this arrangement makes obvious

What gives way first, in order

1 — the sandbox starves the API. Backtests and web requests share node-1’s four vCPU, and a parameter sweep is exactly the kind of job that pins them. You will notice this as the site feeling slow while you are doing research, long before any other limit is near.

2 — bot lookbacks flood the database. Every strategy on every symbol issuing its own query each minute is thousands of small reads. Batch them into one query per minute before adding hardware; it is a code change, not a purchase.

3 — Timescale memory, once bar volume passes what fits in page cache. Then, and only then, hardware.

Scale the stateless out, the stateful up

Horizontal for anything without state: backends, sandbox workers, bot hosts. Add replicas; this is the whole reason k3s is worth the setup, and it costs nothing until you add a node. The first move is giving the sandbox its own node — about nine dollars, and it removes the contention that bites first.

Vertical for the database. Doubling node-2’s RAM is a reboot; sharding a time-series store is a project that will consume weeks and introduce a class of bug you cannot easily test for. Timescale scales vertically well into hundreds of millions of rows. Do not shard until vertical is genuinely exhausted, which on this workload is a long way off.

Kafka scales horizontally by partition, but a single broker handles far more than an IEX feed produces. That is a lever for later, not now.

One limit no amount of hardware moves: Alpaca’s symbol cap and its IEX-only free tier. Collecting more names, or getting consolidated volume rather than one venue’s slice, is a subscription decision. It is worth knowing which of your ceilings you can buy your way past with servers and which you cannot.

Scaling

The two rewrites worth doing, and when

At today’s volume nothing here is CPU-limited — a seven-thousand-bar backtest returns in seconds. These are the two components that break first as scale arrives, and they break along completely different axes.

RankComponentLanguageBreaks when
1Scraper + aggregator, mergedGoA consolidated feed instead of IEX — 100k–1M messages/sec at the open. Python cannot: the GIL serialises it and per-object allocation dominates.
2Backtest inner loop & indicator kernelsRust via PyO3Sweeps get big. A hundred configurations over twenty instruments across five years of minutes is roughly half a billion bar-evaluations — hours in a Python loop.
—Everything elseStays Python / TypeScriptThe API is I/O bound, the bot evaluates once per symbol per minute, and the database bottlenecks long before either language does.

Why Go for one and Rust for the other

The ingest path is concurrency and I/O — goroutines and channels fit it exactly, and Go reaches most of the ceiling for a fraction of the development cost. Move it to Rust only if GC pauses show up in tail latency, which you would see in the metrics rather than guess at.

The backtest path is a numeric inner loop that cannot be vectorised — a trailing stop depends on the previous bar’s stop, which kills the numpy escape hatch. Rust behind PyO3 keeps ctx.sma() and for bar in ctx.bars() exactly as authors write them today while compiling the machinery underneath.

The engine itself must stay Python

It is the highest-CPU component, which makes it look like the obvious target. It is not: your users write strategies in Python, and that is the product. Rewriting it means either they write Rust or you embed an interpreter and inherit both languages’ problems. Only the kernels underneath move.

At scale the wins are architectural before they are linguistic

A Python consumer across twelve Kafka partitions in twelve processes beats a single-threaded Go one. Timescale chunk sizing and compression will move query times more than any rewrite. Batching the bot’s lookback into one query instead of ten thousand matters more than what it is written in.

The honest order is partition, batch, index — then rewrite the one component still hot, chosen from a flame graph rather than from a guess, including mine.

dbt

Where dbt earns its place, and where it does not

dbt is worth adding, but for a narrower job than it is usually given. Two of the three things you might point it at are already better served by something else.

JobUse dbt?Why
Rolling 1m bars into 1h and 1dnoTimescale continuous aggregates do this incrementally and automatically as minutes land. dbt would rebuild in batch — more machinery, staler results.
Filling gaps in collectionnoThat is the reconciler’s job and it needs to call a provider, not run SQL.
Data-quality testsyesThis is the strong fit. Assertions like “no session is short of bars”, “no duplicate timestamps”, “no bar has a high below its low” are exactly what dbt tests express, and they run on a schedule with a readable failure.
Analytics martsyesPer-strategy, per-symbol and per-session performance tables. Batch SQL over settled data, with lineage and documentation — dbt’s home ground.

The tests are the reason to adopt it

The recurring hazard in this whole design is a gap nobody notices until a backtest has already run over it. A dbt test suite turns that from a thing you hope about into a thing that fails loudly on a schedule — and it produces the completeness figure the Lab needs to display rather than requiring separate code to compute it.

Runs as a scheduled job on node-2 beside the database, models living in data-pipeline · dbt/. It reads and writes Timescale and talks to nothing else.

Do not let it become the pipeline

dbt is a batch transformation tool. The moment bar production depends on a dbt run, freshness is bounded by that schedule instead of by the aggregator — and the bot would be deciding on data that is minutes old. Keep it downstream of the live path, never inside it.

Operations

Three small nodes, not one big one

At a thirty to forty dollar budget, three modest machines beat one larger machine — not for capacity, but because Kafka and TimescaleDB stop competing for the same memory, and because a three-node k3s cluster has a real control plane rather than a single point that takes everything with it.

A three-node control plane is not three-node data

k3s with embedded etcd across three servers survives losing one. TimescaleDB with a single replica on a single volume does not. For a research platform that is a reasonable trade — but it means nightly backups off-box are the thing standing between you and losing every bar you have collected, and collection cannot be replayed. Budget for a Storage Box or S3 bucket and test a restore.

Pin the stateful pods with node affinity so their volumes stay attachable, and keep Kafka off the database node — the two of them contending for page cache is the classic way a small cluster starts timing out.

The existing Terraform should be rewritten against the hcloud provider: three servers, a private network, a firewall, the volumes, and DNS. Roughly a hundred lines, and it replaces a directory that currently describes infrastructure you do not run.

Only one inbound port on the whole estate

Everything a browser touches arrives at node-1 on 443. Postgres, Redis and Kafka are reachable only across the private network, which Hetzner does not bill as egress. The firewall rule is therefore short enough to be auditable — and if the database is ever reachable from the internet, something has gone wrong rather than something has been forgotten.

node-1 and node-3 hold no state that cannot be rebuilt from an image and a git checkout. node-2 holds every bar you have ever collected, and collection cannot be replayed. Backups from node-2 to somewhere off the estate are not optional, and restoring one should be something you have actually done once, not something you assume works.

Honest caveats

Four things that will bite if ignored

Publishing a strategy is remote code execution

A published strategy is Python your server runs, and the strategy volume is currently shared across dev, staging and production. With orgs and projects, “a member of any project” would mean “can run code on your host”. Keep publishing org-admin only until the sandbox is genuinely isolated — network denied, memory and CPU capped, no filesystem.

The watermark lies if collection ever stops

A deploy or a crash leaves a hole inside a range still claiming to be whole, and a backtest runs straight over it. That is what bar_gaps and the reconciler are for — and why datasets need a completeness figure in the UI, not just a row count.

A bot is not a backtest

Even with perfect parity of inputs, live adds slippage, partial fills, and a broker that can reject an order. The bot should record intended price alongside filled price from day one, or you will not be able to tell strategy decay from execution cost.

Sources are not interchangeable

Alpaca’s free feed is IEX only and will not line up with a yfinance range beside it. A dataset spanning the watermark spans two sources, and that seam should be visible rather than smoothed over.
